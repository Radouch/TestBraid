## 2. Target directory layout

```text
<domain-directory>/
├── www/                             # Public: served by Apache
│   ├── index.html                   # From frontend/dist
│   ├── assets/                      # From frontend/dist
│   ├── api/
│   │   └── index.php               # From deploy/www/api/index.php
│   ├── media/
│   │   └── .htaccess               # For future published media
│   └── .htaccess                   # From deploy/www/.htaccess
└── testbraid-backend/              # Private: NOT served by Apache
    ├── composer.json
    ├── composer.lock               # Created on first install, commit afterwards
    ├── bin/                        # Private PHP CLI checks
    ├── src/                        # Private PHP source
    ├── schemas/                    # COPY OF ROOT schemas/ FROM SOURCE REPO
    │   ├── test.schema.json
    │   ├── group.schema.json
    │   ├── ...                     # Other canonical schema JSON files
    │   └── fixtures/
    │       └── manifest.json       # Required by composer run test:schemas
    ├── config/
    │   ├── authors.json            # Hashed credentials, generated by setup
    │   └── setup.key               # Temporary SFTP-provisioned setup key
    ├── storage/
    │   └── login-attempts/         # Writable only by the PHP process
    ├── public/
    │   └── index.php               # Actual Slim application
    └── vendor/                      # Installed by Composer on the host
```

The `www/api/index.php` file is only a public bootstrap. Its default path points to the **sibling** directory `testbraid-backend`; the actual PHP app loads its own `vendor/autoload.php` by a relative path. The bootstrap also identifies its actual served `www/` parent for the storage isolation guard, because `DOCUMENT_ROOT` supplied by Apache can be too broad on shared hosting. Author password hashes and the login throttling state must remain **private and writable by the PHP process as appropriate**.

## 3. Prepare frontend locally

Only Node.js/npm are needed on your computer. No local Composer installation is required.

```sh
git clone -b feature/poc-a-foundation https://github.com/Radouch/TestBraid.git
cd TestBraid/frontend
npm install
npm run build
```

The output is `frontend/dist/`. Build and test the default root installation first.

For a **subdirectory** deployment, build with a matching Vite base path (including both slashes):

```sh
npm run build -- --base=/testbraid/
```

Vue Router and the health-check URL use Vite's `BASE_URL`. The default root build uses `/`. In the PHP backend, the default Slim base path is **empty** (domain-root URLs), deliberately independent of Apache's `SCRIPT_NAME` or internal rewrite target. For an actual subdirectory deployment, explicitly configure `TESTBRAID_BASE_PATH=/testbraid` for the PHP web process and deploy the matching Vite build. Also adjust the public bootstrap's relative private path to the actual layout and put the Apache rewrite file in the application directory. Do not set `TESTBRAID_BASE_PATH` for the current root-domain installation.

Do not upload `frontend/node_modules/` or frontend source files to the public web root.

## 4. Upload files to the host

### Recommended: generate a complete deployment directory

The repository deliberately keeps the canonical `schemas/` directory at its **root**, because both the Vue frontend and the PHP backend validate against the same schemas. In the **deployed installation**, PHP expects a private copy at `testbraid-backend/schemas/`. These layouts are intentionally different; do not move the canonical sources or put the schemas under the public `www/` directory.

From the repository root, after building `frontend/dist/`, run:

```sh
node scripts/prepare-deployment.mjs
```

This creates an ignored, disposable `deployment-package/` directory with two top-level directories:

```text
deployment-package/
├── www/                         # Upload contents to the public www/
└── testbraid-backend/           # Upload contents to the private backend/
    ├── composer.json
    ├── bin/
    ├── public/
    ├── src/
    └── schemas/
        └── fixtures/manifest.json
```

Upload the **contents** of each directory to the corresponding server directory via SFTP, overwriting matching *code* files only. The package deliberately excludes `config/`, `storage/`, and `vendor/`: **keep those existing server directories and their contents unchanged**. Do not use synchronization with `--delete` or wipe the remote backend. Run Composer on the server as described below. If a reviewed `backend/composer.lock` exists in your checkout, the script includes it.

The staging command fails if the frontend build or essential schema fixtures are missing; CI verifies the staged paths too. No Composer or database is required on your computer.

### Manual SFTP/rsync alternative

Use SFTP or `rsync`; substitute your real SSH account/paths. **Do not create or guess an absolute server path based on the hostname.**

- Copy **the contents** of `frontend/dist/` into `<domain-directory>/www/`.
- Copy **the contents** of `deploy/www/` into the same `www/` directory, including hidden `.htaccess` files.
- Copy `deploy/testbraid-backend/.htaccess` to the private `testbraid-backend/.htaccess` directory root. This explicitly denies HTTP access to the private backend even if a host exposes a broader document root by mistake. It does not affect PHP `require` / `include` across the filesystem.
- Copy `backend/composer.json`, `backend/public/`, `backend/src/`, `backend/bin/` and the **entire repository-root `schemas/` directory** to their corresponding private paths. In particular, `schemas/fixtures/manifest.json` must end up as `<domain-directory>/testbraid-backend/schemas/fixtures/manifest.json`, not as `<domain-directory>/schemas/fixtures/manifest.json` or under `www/`.
- Do **not** copy `deploy/www/` itself as a nested `www/www` directory.
- Do **not** expose `backend/`, `vendor/`, `storage/` or any password file inside `www/`.

Example `rsync` structure (replace placeholders before running):

```sh
rsync -av frontend/dist/ USER@HOST:/ABSOLUTE/DOMAIN-DIR/www/
rsync -av deploy/www/ USER@HOST:/ABSOLUTE/DOMAIN-DIR/www/
rsync -av deploy/testbraid-backend/.htaccess USER@HOST:/ABSOLUTE/DOMAIN-DIR/testbraid-backend/.htaccess
rsync -av backend/composer.json USER@HOST:/ABSOLUTE/DOMAIN-DIR/testbraid-backend/
rsync -av backend/public/ USER@HOST:/ABSOLUTE/DOMAIN-DIR/testbraid-backend/public/
rsync -av backend/src/ USER@HOST:/ABSOLUTE/DOMAIN-DIR/testbraid-backend/src/
rsync -av backend/bin/ USER@HOST:/ABSOLUTE/DOMAIN-DIR/testbraid-backend/bin/
rsync -av schemas/ USER@HOST:/ABSOLUTE/DOMAIN-DIR/testbraid-backend/schemas/
```

Create the destination `testbraid-backend/public/`, `testbraid-backend/src/` and `testbraid-backend/schemas/` directories with SSH/SFTP if absent. The optional `backend/bin/` test runner can also be copied for schema verification. The entire `schemas/` directory (including fixtures) should be deployed into the private backend.

## 5. Install PHP dependencies over SSH

Log in to the host; run Composer in the **private backend** directory:

```sh
cd /ABSOLUTE/DOMAIN-DIR/testbraid-backend
php -v
composer --version
composer install --no-dev --optimize-autoloader
composer check-platform-reqs --no-dev
composer run test:schemas
```

Before running `test:schemas`, ensure that `testbraid-backend/schemas/test.schema.json` **and** `testbraid-backend/schemas/fixtures/manifest.json` exist. The command runs shared fixtures against PHP's Opis schema validator and publication rules, once installed. If the schemas are absent, Composer can install successfully but validation fails; the test runner now prints a direct instruction instead of an uncaught `json_decode` error. This does not expose test data publicly. The project currently declares PHP 8.1+ for portability; the example host runs PHP 8.5. The Slim requirement is **`^4.15.3`**, avoiding known vulnerabilities in earlier Slim 4 releases.

When `composer.lock` does not exist, the first `composer install` resolves dependencies and creates one. Review and commit that generated lockfile to the repository later so subsequent installations are reproducible. Do not fabricate lockfiles by hand.

If `php -v` on SSH differs from the PHP version serving the website, select the correct CLI binary for Composer and investigate web PHP compatibility separately. Never assume that the CLI and web SAPIs have the same version.

## 6. First-author setup through the browser (no SSH scripts)

The first author can be created from the `/admin` page without invoking any SSH/PHP command. **Live first-author creation was confirmed by the owner on 2026-10-19.** **A private one-time setup key is required** to prevent arbitrary visitors from claiming the first administrator account. There is no unrestricted public sign-up.

After updating the frontend and backend files from `feature/poc-a-auth`:

1. Using SFTP or your hosting file manager, open the **private** `testbraid-backend/` directory beside `www/`. Create the directory `config/` inside it if necessary. Do not create this under `www/`.
2. In a password manager, generate a cryptographically random key of **at least 32 characters**. Create a plain-text file named **`setup.key`** (lowercase) containing only that key, optionally followed by one newline. Upload it as `testbraid-backend/config/setup.key`. Do not commit this file or share the key in issue reports.
3. Ensure the webserver's PHP user can **read** `setup.key` and can **create files in** `testbraid-backend/config/`. It must also be able to write in `testbraid-backend/storage/login-attempts/` (created automatically if the parent is writable). SSH and web PHP users may differ; use appropriate owner/group permissions without exposing private files publicly.
4. Open `https://testbraid.mariebila.cz/admin`. The page detects that no author exists and shows a first-author setup form. Enter the new username, a **minimum 12-character password**, and the one-time key you uploaded.
5. A successful submission creates `config/authors.json` with a **password hash**, logs in the new author and disables first-author setup permanently. The app tries to remove `setup.key` automatically. **Delete it manually over SFTP if it remains** (for example, due to file ownership).
6. Log out and back in using the new username/password. Check that `/api/admin/ping` returns 401 when logged out and succeeds when logged in.

The absence of `setup.key` is intentional: the page shows setup instructions instead of an unsecured account-creation form. After at least one author exists, uploading another `setup.key` **will not reopen registration**, even if the original file is lost or still present. The account JSON file must never be deleted to reset passwords: use a deliberate recovery process instead.

The setup POST route is `/api/auth/setup`. It requires both the private setup key and a valid same-session CSRF token; it uses the same private persistent rate limiter as login. The setup transaction uses a filesystem lock and atomic file replacement to reject parallel attempts.

### Optional SSH provisioning

The existing `php bin/create-author.php alice` CLI provisioner remains available for operators who want it, but **it is not needed** for first-time setup.

### Authentication security

- `/api/auth/session` provides `authenticated`, `setupState` (`needs-key`, `ready`, or `complete`) and a CSRF token. It never reveals the private setup key.
- `/api/auth/login` and `/api/auth/logout` change the native PHP author session; admin API routes are guarded server-side.
- Production uses `Secure`, `HttpOnly`, `SameSite=Lax` cookies; state-changing requests require CSRF. Loopback HTTP is only allowed for local CLI-server integration tests.
- No password, password hash, setup key, or filesystem path is intentionally exposed by the API.

The CI runners use disposable configuration paths: `composer run test:auth` and `composer run test:setup`. Neither test targets the public hosting domain.

## 6A. Private JSON storage increment (Issue #5; live create/read smoke test passed)

The `feature/poc-a-storage` branch adds authenticated endpoints to create/list/rename groups and to create/list/read/update **draft** tests. Publishing tests and browser test editing are deliberately not implemented yet in this storage branch; private media uploading is added by the following issue #6 branch. On 2026-10-19, the owner verified authenticated creation of a group and draft test and successful read-back on the live host; group rename and test update remain tested in CI but not yet manually confirmed on that host. For future upgrades, protect persistent `config/` and `storage/` data before replacing code.

- Private records live in `testbraid-backend/storage/groups/*.json` and `testbraid-backend/storage/tests/*.json` by default. The same repository abstraction reserves `storage/media/` for the subsequent upload increment.
- The PHP web user must be able to create the private `storage/` directory and subdirectories, create lock files and temporary files, and atomically rename completed JSON files. `TESTBRAID_STORAGE_DIR` can relocate storage to another **private** path; never set it inside `www/`.
- Deploy `backend/src/Http/`, `backend/src/Storage/`, and the updated `backend/public/index.php` together with the existing schema and authentication code. New admin endpoints inherit the session and CSRF protections. The frontend has **no** corresponding authoring screens yet.
- Each record uses a server-generated UUID v4 filename. Uploaded data cannot choose filenames, overwrite server-managed timestamps/status, or publish tests. Malformed documents and missing group/media references are rejected.
- A write obtains a per-kind filesystem lock, writes a complete temporary file in the same directory, and renames it into place. This protects an existing record from a partial replacement; it is **not** a multi-file transaction or simultaneous-editor conflict resolution.

### Live host verification (2026-10-19)

The owner confirmed that `/api/admin/groups` returned `{"groups":[]}`, private `composer.json` was not accessible over HTTP, the storage diagnostics reported `groupListing=ok` and `storageUnderServedPublicRoot=false`, and a browser-console smoke test created and successfully read back group `1c03bcff-15bb-471c-b5c4-78d60456e906` and draft test `1533e443-51bc-42f8-a448-79f2538801eb`. These test records remain in private storage for later editor testing. This validates create/read, not every persistence API operation or a future media workflow.

### Verify locally / before any host upgrade

With Composer dependencies installed, from `backend/`:

```sh
composer run test:schemas
composer run test:auth
composer run test:setup
composer run test:storage
composer run test:storage-roots
composer run test:storage-http
```

The storage HTTP test starts its **own loopback-only** PHP server, creates disposable author credentials and private storage under a temporary directory, and verifies authentication, CSRF, group/test CRUD, invalid requests and missing references. It never contacts the deployed domain. The separate storage-failure test checks that a simulated failed atomic rename leaves the original record intact and removes temporary files.

### Diagnose storage failures on shared hosting

When `GET /api/admin/groups` returns HTTP 500 and the host does not expose PHP error logs, a **logged-in author** can visit `GET /api/admin/storage-diagnostics`. It reports only boolean directory checks and a short allowlisted failure category, never filesystem paths, passwords, or raw exception text.

- `storageDirectoryWritable: false` indicates that the web PHP process cannot write the configured private storage directory. CLI user ownership alone is not decisive, especially with ACLs.
- `storageUnderDocumentRoot: true` reports the relationship to PHP's raw `DOCUMENT_ROOT` variable **only**. Some shared hosts report a broader parent directory. This value is not used as the isolation decision when the physical public bootstrap is available.
- `publicRootSource: bootstrap` means the physical, executed `www/api/index.php` supplied the actual served public web root. `storageUnderServedPublicRoot: false` is required for private storage; `true` means the safety guard should reject it.
- `publicRootSource: document-root-fallback` indicates the old bootstrap or a nonstandard direct entry point is still used; deploy the updated public bootstrap to provide the correct physical root.
- `groupListing: failed` plus `failure` distinguishes directory creation/listing failures from unexpected runtime failures; `groupListing: ok` confirms an empty or populated list can be loaded.

**Security verification on the hosting server:** Before using JSON storage, test `https://testbraid.mariebila.cz/testbraid-backend/composer.json` while logged out (or in a private browser window). It must **not** return the actual `composer.json` file: HTTP 403 or 404 are acceptable. An HTML SPA fallback is not proof of Apache isolation; verify the server's domain/document-root mapping if uncertain. If the raw Composer JSON is publicly accessible, stop deployment and correct the public root / deny rules before storing data. **Never test by requesting `config/authors.json` or other sensitive files.**

The `deploy/testbraid-backend/.htaccess` file provides additional Apache access denial for the private subtree if it is ever reached through HTTP; it is not a substitute for configuring the host's actual public root to `www/`. The private backend and storage must remain separate from the *actually served* `www/` directory. The endpoint is authenticated and is read-only apart from the same lazy creation of the empty `groups/` directory that `GET /api/admin/groups` performs. Do not publish these diagnostics through anonymous `/api/health`.

### Back up and restore

Before a deployment or restore, take a consistent private copy of `config/authors.json` and the entire `storage/` directory, retaining group/test/media relationships and permissions. To obtain a consistent snapshot across multiple files, **pause writes during backup**: atomic replacement is only per record. Never expose a backup under `www/`, and never include actual author credentials or storage JSON in Git. After restoring, verify the PHP user can read the private files and write lock/temp files. There is no automated migration or recovery UI yet.

### Apache rewrite configuration verified on this host

The initial deployment's `/api/health` responded with a generic HTTP 500. A minimal single-route rule using `[END]` worked; the complete rules using `[END]` and **without** `Options -Indexes` subsequently worked for all tested pages.

The corrected file is `deploy/www/.htaccess`. It routes `/api/*` to the public bootstrap, serves real assets as files, routes Vue deep links to `index.html` and does not turn missing `/media/` resources into SPA HTML.

The exact cause of the original HTTP 500 was **not isolated**: changing the rewrite flags and removing the `Options` directive both differed from the original configuration. Reuse the tested configuration and avoid assuming every Apache host permits `Options`.

A direct request to `/api/index.php` may return Slim HTTP 404 because the only implemented route is `/api/health`; this is not itself a deployment failure.

Security spot checks:

- `/composer.json` and `/vendor/autoload.php` must not expose PHP dependencies or private files.
- Public `/media/` contains no original private uploads.
- Only the bootstrap PHP file under `/api/` is public; do not put actual backend source or secrets there.

## 8. Troubleshooting

| Symptom | Likely reason / check |
| --- | --- |
| Home works, API returns 503 | Private entry point or Composer `vendor/autoload.php` missing / wrongly located |
| Home works, API returns HTML | Apache rewrite sends `/api/health` to the Vue `index.html` instead of Slim |
| API returns 500 | PHP error or missing/incompatible Composer dependencies; inspect private server logs |
| `/api/health` returns 404 after adding authentication | A prior version incorrectly derived Slim's base path from rewritten `SCRIPT_NAME`; use the fixed backend from `feature/poc-a-auth`, confirm `TESTBRAID_BASE_PATH` is unset for root-domain installations, and retain the verified Apache `.htaccess` |
| Direct `/admin` returns 404 | Missing/inactive `mod_rewrite` or disallowed `.htaccess` |
| API `500` with original rewrite file | Use the verified `deploy/www/.htaccess` with `[END]` and without `Options -Indexes`; inspect Apache error logs if it persists |
| Browser shows API unavailable | Inspect the browser Network tab and open `/api/health` directly |
| SSH PHP differs from web PHP | Use the correct CLI binary for Composer; inspect the website's PHP handler configuration |
| `composer run test:schemas` reports missing `fixtures/manifest.json` or unavailable schemas | The root `schemas/` was not copied into the **private** `testbraid-backend/schemas/`; upload the whole directory, including `fixtures/`, and rerun the test |

The root Apache rewrite template has passed the owner's live smoke test; the media directory's separate `.htaccess`, security hardening and future upload/video behavior have **not** been validated. Report HTTP statuses and relevant error-log lines if an issue occurs; do **not** share passwords, tokens or private config files.

## 9. Installation portability

No hostname or absolute path is hardcoded in Vue or Slim. The PHP base path defaults to domain root and can be overridden explicitly by `TESTBRAID_BASE_PATH` for subdirectory deployments. For other domains, copy the same artifacts and point the domain document root to their deployed public directory.

By default `deploy/www/api/index.php` computes the sibling private backend location relative to itself. If a provider uses another layout, change the deployment template's default path **or** set `TESTBRAID_BACKEND_ENTRY` to the private `public/index.php` path. This customization is deployment configuration, not an application-code fork.

The SPA uses Vite's public base path and Vue Router uses the same base. This allows root and subdirectory deployment (with the appropriate build and rewrite configuration). For hosted public test links, production code must also derive the base URL rather than assume the example domain.
